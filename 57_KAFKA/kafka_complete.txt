1. WHY KAFKA?
================================================================================

PROBLEM: Traditional message queues are limited.
- RabbitMQ: single consumer per message, no replay
- Database polling: inefficient, high latency
- Batch processing: not real-time

KAFKA SOLUTION:
- Distributed, durable, scalable
- Messages persisted to disk (replayable)
- Multiple consumers can read same data
- Handles millions of messages per second
- Perfect for real-time ML pipelines

USE CASES IN AI/ML:
- Real-time fraud detection
- Live recommendation updates
- Streaming feature computation
- Model prediction pipelines
- Log processing for monitoring
- Real-time dashboards

2. KAFKA ARCHITECTURE
================================================================================

┌─────────────────────────────────────────────────────────┐
│                    KAFKA CLUSTER                         │
│                                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐                │
│  │Broker 1 │  │Broker 2 │  │Broker 3 │  ← Servers     │
│  └────┬────┘  └────┬────┘  └────┬────┘                │
│       │             │             │                      │
│  ┌────▼─────────────▼─────────────▼────┐               │
│  │           TOPICS                     │               │
│  │  ┌──────────┐  ┌──────────┐         │               │
│  │  │Partition 0│  │Partition 1│        │               │
│  │  │  [msg1]  │  │  [msg1]  │         │               │
│  │  │  [msg2]  │  │  [msg2]  │         │               │
│  │  │  [msg3]  │  │  [msg3]  │         │               │
│  │  └──────────┘  └──────────┘         │               │
│  └──────────────────────────────────────┘               │
│                                                         │
└─────────────────────────────────────────────────────────┘

KEY CONCEPTS:
- BROKER: Server storing data (cluster = multiple brokers)
- TOPIC: Named category/feed of messages
- PARTITION: Topic split for parallelism (ordering within partition)
- OFFSET: Unique ID for each message in a partition
- PRODUCER: Sends messages to topics
- CONSUMER: Reads messages from topics
- CONSUMER GROUP: Multiple consumers reading in parallel
- REPLICATION: Copies of partitions across brokers (fault tolerance)

================================================================================
3. PRODUCER (Python)
================================================================================

from kafka import KafkaProducer
import json

# Create producer
producer = KafkaProducer(
    bootstrap_servers=['localhost:9092'],
    value_serializer=lambda v: json.dumps(v).encode('utf-8'),
    acks='all',              # wait for all replicas
    retries=3,               # retry on failure
    max_in_flight_requests_per_connection=1  # ordering guarantee
)

# Send message
producer.send('transactions', value={
    'user_id': 12345,
    'amount': 299.99,
    'timestamp': '2024-01-15T10:30:00',
    'merchant': 'Amazon'
})

# Flush (wait for all pending messages)
producer.flush()

BATCH PRODUCING (More Efficient)
----------------------------------
for transaction in transactions:
    producer.send('transactions', value=transaction)
producer.flush()  # send all at once

KEY CONFIGURATION:
- acks=0: Fire and forget (fastest, no guarantee)
- acks=1: Leader acknowledges (balanced)
- acks=all: All replicas acknowledge (safest, slowest)

4. CONSUMER (Python)
================================================================================

from kafka import KafkaConsumer
import json

# Create consumer
consumer = KafkaConsumer(
    'transactions',
    bootstrap_servers=['localhost:9092'],
    group_id='fraud-detection',
    auto_offset_reset='earliest',  # start from beginning
    enable_auto_commit=False,       # manual offset control
    value_deserializer=lambda m: json.loads(m.decode('utf-8'))
)

# Consume messages
for message in consumer:
    print(f"Topic: {message.topic}")
    print(f"Partition: {message.partition}")
    print(f"Offset: {message.offset}")
    print(f"Key: {message.key}")
    print(f"Value: {message.value}")

    # Process message
    process_transaction(message.value)

    # Commit offset manually
    consumer.commit()

CONSUMER GROUPS:
- Multiple consumers in same group share the load
- Each partition consumed by exactly one consumer in a group
- More consumers than partitions = idle consumers
- Scale by adding partitions

6. DELIVERY SEMANTICS
================================================================================

AT-MOST-ONCE:
  Message may be lost, never duplicated.
  Producer sends, doesn't wait for ack.
  Consumer commits offset before processing.

AT-LEAST-ONCE (Default):
  Message never lost, may be duplicated.
  Producer retries on failure.
  Consumer commits offset AFTER processing.
  SOLUTION: Make processing idempotent.

EXACTLY-ONCE:
  Message delivered exactly once.
  Requires: idempotent producer + transactional consumer.
  Kafka supports this with transactions.

IDEMPOTENT PROCESSING:
  def process(message):
      if already_processed(message.id):
          return  # skip duplicate
      # process...
      mark_as_processed(message.id)

8. MONITORING & OPERATIONS
================================================================================

KEY METRICS TO MONITOR:
- Messages per second (throughput)
- Consumer lag (how far behind consumers are)
- Broker health
- Partition distribution
- Disk usage
- Network I/O

CONSUMER LAG:
- Lag = latest offset - consumer offset
- High lag = consumers can't keep up
- Action: add consumers or partitions

11. COMMON MISTAKES
================================================================================

1. Too few partitions: limits parallelism
   RIGHT: Start with enough partitions (e.g., 12+ for production)

2. Not handling consumer rebalancing
   RIGHT: Process messages quickly, commit frequently

3. Not using consumer groups
   RIGHT: Use groups for parallel processing

4. Auto-commit offsets
   RIGHT: Commit after successful processing

5. Not monitoring consumer lag
   RIGHT: Set up alerts for high lag
