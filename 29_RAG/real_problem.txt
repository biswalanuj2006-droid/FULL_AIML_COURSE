================================================================================
REAL PROBLEM - 29 RAG
================================================================================

PROBLEM A (THE CLASSIC): "I built a RAG agent. I chunked my docs,
embedded them, set up the vector store, and wired it to an LLM. It
'works' - but it gives WRONG answers. It confidently states things that
are not in my documents, contradicts the docs, or hallucinates numbers.
How do I figure out what is broken, and how do I actually fix it?"

--------------------------------------------------------------------------------
STEP 1 - HOW TO FIGURE OUT WHERE THE FAILURE IS (the diagnostic tree)
--------------------------------------------------------------------------------
A RAG answer is the product of 4 stages. A wrong answer means ONE (or
more) of these is broken. NEVER tune the prompt first - you must first
locate the stage. Work through this tree in order:

  Q1. Was the right information retrieved at all?
      Test: for 10 known questions, print the top-5 retrieved chunks
      (text, not just the answer). Do the chunks actually contain the
      answer?
        YES  -> go to Q2 (retrieval is fine, generation is the problem)
        NO   -> retrieval problem (see STAGE 1 below)

  Q2. Does the model answer from the chunks, or from its own memory?
      Test: ask a question whose correct answer CONTRADICTS common
      knowledge, but is in your docs. If the model answers with the
      common-knowledge version, it is ignoring the context (see
      STAGE 2). If it answers with the doc version, fine - go to Q3.

  Q3. Is the retrieved chunk too big / too small / malformed to answer?
      Test: paste ONE retrieved chunk manually into the chat with the
      question (no RAG system). If the model still cannot answer, the
      chunk itself lacks the answer or is too noisy -> chunking /
      document-quality problem (see STAGE 3).

  Q4. Is the LLM prompt telling it to be honest about uncertainty?
      If the prompt says "always answer", the model will fabricate
      rather than say "not in the docs" (see STAGE 4).

80% of "RAG gives wrong answers" reports are STAGE 1 (retrieval) or
STAGE 3 (chunking), NOT the model. Most people debug the model.

--------------------------------------------------------------------------------
STEP 2 - STAGE-BY-STAGE FIXES
--------------------------------------------------------------------------------
STAGE 1 - RETRIEVAL PROBLEMS (chunks returned do not contain the answer)
  Common causes and fixes:
  1. Chunks too small -> answer is split across chunks; raise chunk size
     (e.g. 500 -> 1000 tokens) or use overlap (10-15%).
  2. Chunks too large -> the one good sentence drowns in noise; embed
     smaller units and map them back to larger parent chunks for
     context (parent-document retriever).
  3. Bad embeddings for the domain: generic models mishandle jargon.
     Test with a small labeled set; try a domain fine-tune or a
     stronger embedder. Compare with BM25 (lexical) - sometimes exact
     keyword match beats semantic search; use HYBRID search.
  4. top_k too small: raise from 3 to 8-10, or add reranking so more
     candidates can be considered then re-ranked.
  5. Query is a full question, docs are phrased as statements: rewrite
     the query (HyDE - generate a hypothetical answer and embed that).
  6. Metadata not filtered: the right chunk exists but is filtered out;
     filter on date/source AFTER similarity search, not before.

STAGE 2 - MODEL IGNORES THE CONTEXT (answers from memory)
  1. Context is placed AFTER the instruction or buried; put context
     immediately before the question.
  2. Instruction is vague: say "Answer ONLY from the context. If the
     context does not contain the answer, reply exactly: I don't know."
  3. Some models ignore long contexts: move the most relevant chunks to
     the FRONT (retrieval order matters - "lost in the middle").

STAGE 3 - CHUNK / DOCUMENT QUALITY
  1. Tables, PDFs, code blocks are destroyed by naive text extraction.
     Use layout-aware extraction (pdfplumber, unstructured, layout
     parsers) before chunking.
  2. Deduplicate near-identical chunks (boilerplate, repeated headers).
  3. Add "chunk title + source + section" so the model can disambiguate
     when two chunks contradict each other.

STAGE 4 - HALLUCINATION PRESSURE
  1. Prompt must permit "I don't know" and forbid guessing.
  2. Lower temperature (0.0-0.2) for grounded answers.
  3. Add a faithfulness check: ask a second model call "Does the answer
     follow from the context?" and reject/flag when it does not.
  4. Add citations; if the user (or an automated grader) can't verify,
     treat as ungrounded.

--------------------------------------------------------------------------------
STEP 3 - THE DEBUGGING SCRIPT (run this BEFORE changing anything)
--------------------------------------------------------------------------------
Run this on your real questions. It prints exactly WHERE the pipeline
fails. This is the most important code in this file - it converts
"my agent is wrong" into "retrieval fails on 6/10 questions".

  # debug_rag.py - locate the failing stage of a RAG pipeline
  import numpy as np
  from typing import List

  def debug_rag(questions: List[str],
                expected_answers: List[str],
                retrieve,          # q -> List[str] of chunks
                generate,          # (q, chunks) -> answer
                embed):            # str -> vector (for similarity check)
      """For each question, report: did retrieval find the answer?
      Does the generated answer match the expected one?"""
      retr_hits, gen_hits = 0, 0
      for q, exp in zip(questions, expected_answers):
          chunks = retrieve(q)
          # --- retrieval check: is the expected answer in top-5 chunks?
          in_top5 = any(exp.lower()[:30] in c.lower() for c in chunks[:5])
          # --- generation check: does the model echo the expected fact?
          ans = generate(q, chunks)
          match = exp.lower()[:30] in ans.lower()
          print(f"\nQ: {q}")
          print(f"  retrieval hit : {in_top5}  ({len(chunks)} chunks)")
          print(f"  answer correct: {match}")
          if not in_top5 and match:
              print("  !! suspicious: correct answer WITHOUT retrieval = model "
                    "used memory; context is not being grounded on")
          retr_hits += in_top5
          gen_hits  += match
      print(f"\n=== retrieval hit-rate: {retr_hits}/{len(questions)}  "
            f"| answer hit-rate: {gen_hits}/{len(questions)}")
      print("=== If retrieval < 0.8  -> fix chunking/embeddings/hybrid")
      print("=== If retrieval high but answers low -> fix prompt/grounding")

  # --- similarity check: are your embeddings any good on this domain?
  def sanity_check_embeddings(embed, queries, positives):
      """Similar queries should be closer than unrelated ones."""
      for q, p in zip(queries, positives):
          vq, vp = np.array(embed(q)), np.array(embed(p))
          cos = vq @ vp / (np.linalg.norm(vq) * np.linalg.norm(vp))
          print(f"sim({q!r:.40}, {p!r:.40}) = {cos:.3f}")

--------------------------------------------------------------------------------
STEP 4 - A CORRECT, MINIMAL, DEBUGGABLE RAG AGENT (fixes applied)
--------------------------------------------------------------------------------
The agent below is intentionally small so every piece is inspectable.
It applies the fixes: hybrid retrieval, chunk titles, top_k + rerank
slot, grounded prompt, faithfulness self-check, and a debug mode that
prints the retrieved chunks. Study it; this is the shape of a
production-grade minimal system.

  # proper_rag_agent.py
  import os
  from dataclasses import dataclass

  # --- 1. CHUNKING with overlap + titles (fixes STAGE 1/3) ---------------
  def chunk_text(text: str, title: str, size: int = 800,
                 overlap: int = 120) -> list:
      words = text.split()
      chunks, i = [], 0
      while i < len(words):
          piece = " ".join(words[i:i + size])
          chunks.append(f"[Source: {title}]\n{piece}")
          i += size - overlap                       # overlap keeps
      return chunks                                 # context intact

  # --- 2. HYBRID RETRIEVAL: dense (embeddings) + sparse (BM25-like) ------
  from collections import Counter
  from math import log

  def bm25_score(query_tokens: set, doc_tokens: list,
                 df: dict, n_docs: int) -> float:
      tf = Counter(doc_tokens)
      return sum(log((n_docs - df.get(t, 0) + 0.5) / (df.get(t, 0) + 0.5)
                     + 1.0) * tf.get(t, 0) for t in query_tokens)

  def hybrid_search(query: str, chunks: list, embed, top_k: int = 6):
      vq = embed(query)
      dense = sorted(
          ((np.dot(vq, embed(c)) /
            (np.linalg.norm(vq) * np.linalg.norm(embed(c)) + 1e-9)), i)
          for i, c in enumerate(chunks))[::-1][:top_k * 3]
      qtoks, tok_docs = set(query.lower().split()), [c.lower().split()
                                                      for c in chunks]
      df = Counter(t for doc in tok_docs for t in set(doc))
      sparse = sorted(((bm25_score(qtoks, tok_docs[i], df,
                                   len(chunks)), i) for i, _ in dense),
                      reverse=True)[:top_k]
      return [chunks[i] for _, i in sparse]   # rerank-slot: swap in a
      # reranker (e.g. cross-encoder) here for precision at top-k

  # --- 3. GROUNDED GENERATION + FAITHFULNESS SELF-CHECK (fix STAGE 2/4) --
  SYSTEM = ("Answer ONLY from the provided context. If the context does "
            "not contain the answer, reply exactly: NOT IN CONTEXT. "
            "Never use prior knowledge. Cite the [Source] of each claim.")

  def generate_grounded(client, question: str, chunks: list,
                        temperature: float = 0.0) -> str:
      context = "\n\n".join(chunks)
      answer = client.chat.completions.create(
          model="your-model",
          messages=[{"role": "system", "content": SYSTEM},
                    {"role": "user", "content":
                     f"Context:\n{context}\n\nQuestion: {question}"}],
          temperature=temperature).choices[0].message.content
      if answer.strip().upper() == "NOT IN CONTEXT":
          return answer
      # Faithfulness gate: does the answer follow from the context?
      verdict = client.chat.completions.create(
          model="your-model",
          temperature=0.0,
          messages=[{"role": "user", "content":
                     "Does the answer below follow ONLY from the context? "
                     "Answer YES or NO and quote the supporting sentence.\n\n"
                     f"CONTEXT:\n{context}\n\nANSWER:\n{answer}"}]
      ).choices[0].message.content
      return answer if verdict.strip().upper().startswith("YES") \
                    else "NOT IN CONTEXT (ungrounded answer rejected)"

--------------------------------------------------------------------------------
STEP 5 - COMMON BUGS FOUND IN "WRONG ANSWER" RAG SYSTEMS (checklist)
--------------------------------------------------------------------------------
  [ ] Embedding the QUERY and DOCS with different models / no normalization
  [ ] Cosine vs dot-product mismatch with the vector store's metric
  [ ] Retrieving from the WRONG collection/namespace (old version of docs)
  [ ] Forgetting to add the prompt's context to the token budget; context
      silently truncated by the model's max length
  [ ] PDF tables turned into gibberish by text extraction
  [ ] Duplicated documents inflate retrieval with near-identical chunks
  [ ] Test questions written from the docs but retrieval evaluated
      against the answer text (circular) - grade retrieval on chunks
      that actually CONTAIN the answer
  [ ] No eval set: if you cannot measure retrieval hit-rate and answer
      accuracy on 50-100 known questions, you cannot debug, only guess

PROBLEM B: "Retrieval is perfect (hit-rate 0.95) but the agent still
gives wrong answers."
WHY: the failure moved to generation - the model paraphrases but
distorts numbers, merges two different entities from two chunks, or
answers from memory when the context feels "familiar".
HOW TO SOLVE
  1. The faithfulness gate in STEP 4 catches most of these; log every
     rejection and inspect the pattern.
  2. Entity-level errors: ask for the answer to quote the exact chunk
     sentence before answering; compare spans.
  3. Merging errors: detect when the answer cites 2+ sources and the
     model conflates them; use structured extraction (JSON with
     "answer" + "evidence") instead of free prose.

PROBLEM C: "In production the agent was great for a month, then started
answering wrong."
WHY: the docs changed (new chunking parameters?), the embedder/LLM
model version was updated silently, or the index was rebuilt with stale
documents. This is drift in the KNOWLEDGE layer, not the model.
HOW TO SOLVE
  1. Version the index: store collection name = f"docs_v{major}.{minor}"
     and log which collection every request hit.
  2. Re-run the STEP 3 debug harness on your 100 golden questions after
     ANY index rebuild or model bump, before shipping.
  3. Monitor: retrieval hit-rate on sampled logged questions + answer
     rejections over time; alert on drops.
